# Gravitas Multi-Class Memory & Provenance Architecture (Wave 12C.5)

## 1. Principles of Memory in Gravitas

Gravitas explicitly rejects the naive anti-pattern of dumping all system information into an unpartitioned vector database. Unstructured vector storage causes semantic drift, context pollution, hallucinated facts, and loss of verifiable provenance.

$$\text{Memory} \neq \text{Unstructured Vector Store}$$

Instead, Gravitas partitions memory into **5 Distinct Memory Classes**, each optimized for its specific durability, retrieval speed, query semantics, and cryptographic verifiable provenance.

---

## 2. The 5 Memory Classes

| Memory Class | Storage Engine & Format | Retention Lifecycle | Query Modality | Example Contents |
| :--- | :--- | :--- | :--- | :--- |
| **1. Operational State** | In-Memory FSM / Fast Key-Value (Redis/SQLite) | Ephemeral / Active Run | Direct key lookup & FSM event dispatch | Active task FSM states, lock leases, worktree paths, worker process handles, SSE sequence counters. |
| **2. Episodic History** | Append-Only Event Log (JSONL / SQLite) | Permanent / Tamper-Evident | Chronological scans, run ID lookups, audit replay | Historical `GravitasEvent` stream, run timelines, state transitions, command execution traces. |
| **3. Structured Domain Memory** | Relational / Graph DB (SQLite / Embedded Graph) | Permanent / Schema-Enforced | Exact relational SQL queries & graph traversals | Concept mastery graph, academic syllabus topics, business lead records, contacts, calendar commitments. |
| **4. Semantic Knowledge** | Chunked Markdown + Local Embeddings (Chroma/SQLite-vss) | Permanent / Versioned | Hybrid keyword (BM25) + dense cosine similarity | Technical documentation folios, research paper excerpts, API references, architecture decision records. |
| **5. User Preferences** | Validated JSON Schemas (`preferences.json`) | Durable / Explicit User Edits | Direct config read | Work hours, quiet hour boundaries, notification channels, opt-in health tracking, theme tokens. |

---

## 3. Strict Epistemic Taxonomy: Facts vs. Inferences

A critical design flaw in AI agent architectures is conflating model speculation with established reality. In Gravitas, every memory record has a mandatory **Epistemic Class**:

| Epistemic Class | Definition | Verification Source | Can Be Treated as Absolute Fact? |
| :--- | :--- | :--- | :---: |
| **`FACT`** | Cryptographically verified or objectively observed datum. | Direct CLI output, git SHA, HTTP status 200, file checksum. | **YES** |
| **`HISTORICAL_EVENT`** | Verifiable system event recorded in the immutable log. | Timestamped `GravitasEvent` emitted by orchestrator. | **YES** |
| **`USER_PREFERENCE`** | Explicitly declared directive configured by the human operator. | Direct user configuration in UI/CLI settings. | **YES** |
| **`INFERENCE`** | A synthetic deduction generated by an LLM reasoning role. | LLM completion output. | **NO (Treated as Hypothesis)** |
| **`RECOMMENDATION`** | A suggested course of action proposed by an agent role. | Agent planning output. | **NO (Requires Human Approval)** |

## 4. Provenance Metadata Contract

Every stored memory item must answer five immutable provenance questions:

```typescript
export interface ProvenanceRecord {
  /** 1. Exact Source: Component, CLI, or API that produced this record */
  readonly sourceComponentId: string

  /** 2. Timestamp: Cryptographically verifiable ISO-8601 creation time */
  readonly createdAt: string

  /** 3. Status & Confidence: Epistemic class and statistical certainty (0.0 - 1.0) */
  readonly epistemicClass: 'FACT' | 'HISTORICAL_EVENT' | 'USER_PREFERENCE' | 'INFERENCE' | 'RECOMMENDATION'
  readonly confidenceScore: number

  /** 4. Context Scope: Permitted access domain (e.g., 'PROJECT', 'LEARNING', 'BUSINESS') */
  readonly contextScope: ContextScopeId

  /** 5. Access Control: Explicit list of roles authorized to view this record */
  readonly authorizedRoles: ReadonlyArray<string>
}
```
