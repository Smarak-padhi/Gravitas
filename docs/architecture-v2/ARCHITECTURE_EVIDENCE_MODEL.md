## 1. Epistemological Foundations & Claim-Relative Evidence

The GRAVITAS Architecture Arena rejects subjective assertions, ungrounded confidence scores, and democratic consensus. In their place, it establishes an explicit epistemological principle:

$$\mathbf{EVIDENCE\ QUALITY\ IS\ CLAIM-RELATIVE}$$

Evidence quality does not exist as a universal, context-free linear ladder where one category unconditionally trumps another. Instead, the evidential authority of an artifact depends strictly on the **type of claim** being evaluated:
* **API Contracts & Language Semantics:** Official specifications (ECMA, W3C, RFCs) and compiler source code dominate.
* **Host Execution & Real Latency:** Reproducible local observations and empirical test scripts on the target OS (Windows 11) dominate external synthetic claims.
* **Operational Friction & Failure Modes:** Credible practitioner reports, post-mortems, and issue trackers provide essential, primary insight into edge cases, leaks, and crashes.
* **Maintenance & Supply Chain Health:** Public commit velocity, release frequency, governance models, and open bug handling provide authoritative telemetry on abandonment risk.

An agent stating an opinion with 99% confidence has zero architectural weight without verifiable supporting citations. Conversely, empirical limitations evidenced by reproducible test scripts or issue trackers directly constrain architectural feasibility.

### Contextual Role of Popularity & Community Signals
Signals such as GitHub star counts, social media buzz, and corporate sponsor lists have **near-zero evidential weight** for claims regarding:
* Correctness and bug-freedom
* Security boundaries and process isolation
* Real runtime performance and memory efficiency
* Architectural suitability for GRAVITAS

However, such signals provide **weak contextual evidence** regarding:
* Ecosystem scale and probability of third-party community support
* Availability of pre-built integrations, type definitions, and tooling
* Likelihood of long-term maintainer commitment

Under no circumstances may popularity metrics dominate an architecture decision or override an empirical, security, or financial constraint.

## 2. Seven Evidence Quality Classes & `EvidenceFitness`

Every evidentiary claim ingested or generated by a Scout is classified into one of seven formal quality classes:

1. **`PRIMARY_EVIDENCE`:** Immutable primary artifacts: official specifications (RFCs), compiler source code, Git commit histories, and OS system headers. Authoritative for contracts and capabilities.
2. **`REPRODUCIBLE_OBSERVATION`:** Empirical observations recorded locally under documented test conditions with published reproduction scripts (e.g. local CLI version probing, memory measurement scripts). Authoritative for local host behavior.
3. **`OFFICIAL_CLAIM`:** Explicit statements published by core project maintainers in official documentation, READMEs, or release announcements. Authoritative regarding intended design, but subject to bugs or drift.
4. **`THIRD_PARTY_MEASUREMENT`:** Benchmarks or technical analyses conducted by independent third parties where the testing methodology, environment, and code are fully disclosed. Evaluated with strict benchmark incomparability checks.
5. **`COMMUNITY_EXPERIENCE`:** Reports from practitioners in issue trackers, forums, or post-mortems documenting real-world friction, failure modes, or edge-case behavior. Highly authoritative for operability and maintenance risks.
6. **`ARCHITECTURAL_INFERENCE`:** Deductive conclusions reached by an agent through valid logical synthesis of verified facts (e.g. "Because Framework X uses synchronous Win32 message pumping, it cannot run in a headless Windows service without a virtual desktop").
7. **`SPECULATION`:** Unverified hypotheses, intuitive claims, or recollections from general LLM training data. Holds zero gating weight.

### The `EvidenceFitness` Evaluation Matrix

To determine the final weight of an evidence item in an architectural debate, the Synthesizer evaluates `EvidenceFitness` across 10 orthogonal dimensions:

## 4. Benchmark Incomparability Model

Scouts frequently discover conflicting benchmark claims (e.g. "Framework A is 5x faster than Framework B"). The Arena prohibits simplistic comparisons of mismatched benchmarks:

### Criteria for Benchmark Incomparability
A pair of benchmarks is flagged as `INCOMPARABLE_BENCHMARKS` if any of the following parameters differ:
1. **Operating System & Kernel Version:** e.g. Linux epoll vs. Windows IOCP.
2. **Hardware Environment:** Bare metal vs. virtualized cloud instance vs. local desktop.
3. **Workload Definition:** Synthetic "Hello World" vs. real-world structured payload parsing.
4. **Client/Server Proximity:** In-memory localhost vs. network latency.
5. **Runtime Compiler Flags:** Debug build vs. optimized production flags with LTO.

### Architectural Policy on Benchmark Disputes
$$\textbf{Disputed Synthetic Benchmark } \longrightarrow \textbf{ REQUIRES\_EXPERIMENT}$$
When two proposals clash on performance claims derived from disparate third-party benchmarks, the Synthesizer **must not** pick a winner. The dispute must be recorded as an unresolved empirical unknown to be resolved by a localized, controlled experiment in a subsequent wave.

## 5. Contradiction Registry & Lifecycle

When independent Scouts produce diametrically opposed claims supported by credible sources, the Arena does not suppress the minority claim. It instantiates a formal `Contradiction` record.

```typescript
export type ContradictionStatus =
  | 'UNRESOLVED'
  | 'RESOLVED_BY_VERSION_DISCRIMINATION'  // e.g. Source A tested v1.2, Source B tested v2.0
  | 'RESOLVED_BY_ENVIRONMENT_DISCRIMINATION' // e.g. Works on Linux, fails on Windows
  | 'RESOLVED_BY_EMPIRICAL_PROBE'        // Local test confirmed one claim
  | 'RESOLVED_BY_TIER_OVERRIDE'          // Primary source proved official claim was outdated
  | 'PERMANENT_DESIGN_TRADE_OFF';        // Genuine architectural divergence

export interface Contradiction {
  readonly contradictionId: string;
  readonly questionId: string;
  readonly claimA: {
    readonly statement: string;
    readonly evidenceRef: string;
    readonly proponentScoutId: string;
  };
  readonly claimB: {
    readonly statement: string;
    readonly evidenceRef: string;
    readonly proponentScoutId: string;
  };
  readonly suspectedCause: string;
  readonly status: ContradictionStatus;
  readonly resolutionDetails?: string;
  readonly impactOnDecision: 'BLOCKING' | 'SIGNIFICANT' | 'MINOR' | 'NEGLIGIBLE';
}
```

### Invariant: Contradictions Survive into the Decision Packet
Any `Contradiction` whose status remains `UNRESOLVED` at the end of the Arena cycle **must** be explicitly presented in Section 6 of the `ArchitectureDecisionPacket`. The Synthesizer is strictly forbidden from hiding or arbitrarily deciding contradictions.
